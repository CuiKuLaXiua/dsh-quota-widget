方案 B 的关键设计细节（如果选它）

问题处理方式
网关不支持某些分组 选了 项目/会话/工具/小时 时，自动把"来源"里的网关置灰，并显示一行： 「网关流量无此维度，已排除」。不能静默丢掉 —— 否则用户以为网关那天没用量。
日界口径 网关按 UTC+8、本机按本机时区。表头标注「含网关」，并在 tooltip 里写清两者日界不同； 若本机不是 +8，按日期聚合时会有边界日的 1 天偏差，需在脚注说明。
账号隐私 网关桶键含 accountId。默认不提供"按账号分组"，若要提供则脱敏成 账号 1/2/3（与现有 gatewayReport 的做法一致）。
"存为视图" 把当前（范围+分组+筛选+指标）存进 localStorage，最多 8 条，可选名字。 不做跨设备同步（本仓没有宿主配置文件）。
导出 复用现有 CSV 导出风格；导出内容 = 当前视图的表格（所见即所得），不是原始 events。
性能 查询走 sqlite 聚合（GROUP BY），不拉 events 全量。上限：30 天 × ~20 模型 × ~6 渠道 ≈ 3600 行，聚合耗时 <10ms。
已知边界 ① 只有 90 天保留窗口；② 清空账本后查不到（历史下限被推进）； ③ 网关侧只有日聚合，查不到逐笔；④ 项目为空的历史事件归「—」桶。

我推荐 B。理由是"自定义组合查询"的核心价值在换视角（按项目看 / 按渠道看 / 按日看）， 而不是"筛子更细" —— A 的筛选维度其实已经散落在「用量统计」的排行卡里了，单独做个 tab 收益不大。 C 最漂亮，但会引入第三套图形代码，且"20 个模型堆叠"这类问题要额外做 Top-N 合并，成本容易失控。

无论选哪个，建议同时做：① 表头写明是否含网关；② 空结果时给"为什么空"（是没数据、还是被筛选排除了）；③ 时间范围与「用量统计」的 meterRange 互不影响（查询台是独立上下文，跟着主界面变会让人困惑）。
